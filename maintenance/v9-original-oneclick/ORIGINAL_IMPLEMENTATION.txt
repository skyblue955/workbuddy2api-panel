一、入口与调度
前端任务行点击一键完成，POST /panel/api/accounts/{uid}/tasks/auto，body包含task_code。
后端accountTaskAuto -> autoActionFor -> autoActions中对应run函数 -> 回读task -> 达标才claim。
全量按钮POST /panel/api/accounts/{uid}/tasks/auto_all -> accountTaskAutoAll -> runAutoAll。
runAutoAll先default/MP分别报名，再按动作表顺序执行；已有claimed或claimable的任务直接跳过动作并尝试补领。
成长队列runGrowthQueued/task_sweep是另外的调度路径，不是前端单任务handler的别名。
原提交位置：internal/panel/autotask.go autoActions约49；accountTaskAuto628；runAutoAll1135；accountTaskAutoAll1271。

二、chat_5原实现（原autotask.go:766起）
runChat5先读当前target/current，计算差额，再调用Upstream.ReportChatActivity，不调用模型聊天接口。
报告通过/v2/report发送chat_request_send事件；事件成功返回“已补报”，是否真正达标由外层后续任务回读判断。
原函数与本轮基线的任务执行体未改；本轮也不调整事件字段、指纹或补造实际未发生的对话记录。
因此不能把“最多5次deepseek真聊天”称作原runChat5的原样测试；v8记录已明确其独立genuine workflow性质。

三、专家/专家团（原autotask.go:1085起）
expert_5 -> runExpertUse -> runExpertBatch(agent,5)。
Expert_team_use_3 -> runExpertTeamUse -> runExpertBatch(team,3)。
链路是：查询专家市场 -> 召唤事件 -> DesktopChatWithExpert实际聊天并提取服务端request ID -> 使用事件 -> 外层回读/领奖。
不是客户端GUI自动化，也不是只填专家名字的普通网关聊天。
已知局限：DesktopChatWithExpert的id成功不等于完整回答；runExpertBatch部分成功仍返回nil error。
这些已有v5/v6证据，本轮不冒充新发现，不为点亮任务而增强未发生的使用事件。

四、其他动作
资料库、模板、灵感、自动化、Buddy应用等多项旧动作只发送对应行为事件，不实际阅读、使用模板、创建自动化等。
Model_chat_GLM5.2是accept+真实模型对话+模型对齐报告；first_buddy还会接受协议并领养；外观动作还调用设置API。
小程序专属任务使用miniprogram口径，不能只因默认列表有相似字段就跨口径领奖。
本轮不运行全量auto_all，避免把报名、聊天、协议、领养、报告等不同副作用一起执行。

六、本轮可独立复现的新修复点
单任务accountTaskAuto只跳过Claimed，已达标但未领取仍先act.run；全量runAutoAll与成长队列已有“达标直接领奖”保护。
后果：已达标的模型/专家任务仍可能重复真实聊天、报名或其他动作；动作失败还会阻断原本可进行的领奖。
修复原则：只有before.CanClaimReward()为真时跳过动作，仍保留同口径回读和原领奖资格/回执判断；不把过期/锁定/未知进度当达标。
作用是避免重复操作，不让未达标任务凭空完成；单项action跳过也不等于顶层skipped（避免UI绕开领奖失败判断）。
具体baseline/modified/rollback同输入证据见VERIFICATION.txt。
