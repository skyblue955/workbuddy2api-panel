Optional third-party Open API connector prerequisites (NOT required for existing ordinary-account gateway login)
The original project still uses personal-account plugin/device authorization (panel Add Account or login.sh); no developer registration is required for that route. Its upstream-supplied authUrl carries session context, so simply visiting the generic /login/ page is not equivalent. Original login completion also triggers check-in/global registration/trial actions; these must be separated or explicitly approved before read-only account acceptance. The following steps apply ONLY when opting into the new Open API redemption channel:
1. https://open.workbuddy.cn/ : create/enable a third-party credits app, register exact redirect URI and request user.credit.exchange scope. Reference https://open.workbuddy.cn/docs/third-party-app and /docs/openapi.
2. Keep client secret in a local process environment WORKBUDDY_OPEN_CLIENT_SECRET or inject from a password manager; never paste into chat, command arguments, source or logs. Ensure separate private directory exists (mode0700).
3. Generate authorization URL and one-use state file:
  /private/tmp/workbuddy-openapi authorize -client-id APP_ID -redirect-uri REGISTERED_URI -state-file /PRIVATE/DIR/oauth-state.json
Open printed official URL yourself and approve the grant. State/session expires locally after15minutes; no account login is automated. No local callback listener is provided: use a registered callback you control to collect code/state locally, not in this chat.
4. Pipe one JSON object {"code":"AUTH_CODE","state":"RETURNED_STATE"} from a private file/stdin into:
  /private/tmp/workbuddy-openapi exchange -state-file /PRIVATE/DIR/oauth-state.json -token-file /PRIVATE/DIR/openapi-token.json
The command checks saved state before token exchange, refuses an existing token destination, writes OAuth token metadata0600 and consumes state. A .used marker prevents resubmitting the same session after an uncertain exchange/save failure; start a new authorization flow with a fresh state filename instead of replaying. If token is saved but state deletion fails, success output explicitly reports cleanup pending and the marker prevents reuse. Token is not printed. Token expiry uses actual expires_in+obtained_at, and scope must include user.credit.exchange. No automatic refresh daemon or panel credential migration in this candidate; refresh helper exists only as a library.

Redemption (a separately approved, state-changing action)
Prepare private request JSON containing either code or gift_key+gift_code plus a caller-created stable request_id (8–64chars). Never put codes in command arguments or chat.
Dry-run (no network):
  /private/tmp/workbuddy-openapi redeem < /PRIVATE/DIR/redemption-request.json
Only after explicit user approval of this specific redemption:
  /private/tmp/workbuddy-openapi redeem -execute -token-file /PRIVATE/DIR/openapi-token.json < /PRIVATE/DIR/redemption-request.json
Output only confirmation flow_no/credits. Never generate a different request_id to retry an uncertain outcome. There is no local crash-safe redemption ledger: archive the request securely BEFORE execute and use upstream reconciliation. Duplicate success/idempotency is mock-tested, not live-verified. Application approval/token grant do not guarantee a valid code or earned credits.
